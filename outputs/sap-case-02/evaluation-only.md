# SAP 사례: 업무 추출 정답표 초안

이 문서는 대화를 검토해 작성한 평가용 초안입니다. 사용자가 MIGO 처리와 서류 제출을 각각 확인해야 한다는 업무 흐름을 확인했습니다. 실제 SAP 처리 결과를 직접 확인한 정답은 아닙니다. 자동 추출 프로그램의 결과나 ML 예측 결과가 아닙니다. 추출 모델의 입력에 이 정답표를 넣지 않습니다.

## 실험 조건

- 가정: 화요일 오후 2시에 원이정이 갑자기 부재한다. 실제 있었던 공백이라는 뜻은 아니다.
- 입력: `../slack-mcp/collected/sap.json`의 S001~S006.
- 업무 시각은 메시지 본문의 화요일 11시 / 13시 30분을 사용한다. Slack 게시 날짜는 재현 데이터를 올린 시점이므로 업무 날짜로 사용하지 않는다.
- 실제 작성 계정 대신 본문의 발신자·수신자를 사용한다.
- 증거는 대화상 보고를 뜻한다. SAP와 이메일 원문을 직접 검증하지 않았다.

## 시간·관계·불확실성

- 전체 PR/PO 마감: 이번 주 수요일이라고 원이정이 알고 있음(S002). 확정된 마감 공지는 없으므로 재확인 대상이다.
- 제출 목표: 화요일 퇴근 전(S005). 개인이 밝힌 계획이며 정확한 시각은 없다.
- 작업 순서: MIGO 처리 후 제출(S005). 구체적인 SAP 절차는 추가하지 않는다.
- MIGO와 제출은 대화 맥락상 WP1/WP2에 관련된 것으로 추론할 수 있지만 각각 별도 작업인지 명시되지 않았다. 두 건씩 임의로 복제하지 않는다.
- 원이정은 MIGO·제출의 실행 의사를 밝힌 담당자다. 대체 담당자 유무와 접근 권한은 알 수 없다.
- 이혜정의 정상환 대상 메일 발송은 계획(S003)이다. 실제 발송했거나 그 메일 때문에 승인됐다고 단정하지 않는다.

## 공백 발생 시 인수인계 초안

다음은 위험도 모델의 순위가 아니라, 미확인 사항을 해결하기 위한 확인 순서다.

1. MIGO가 이미 처리됐는지 확인한다. 대화에는 실행 계획만 있다.
2. 이혜정에게 PO번호가 있는 메일과 구체적인 서류 정렬 순서를 확인한다.
3. 마충렬에게 서류 수령 여부를 확인한다. 미제출이면 처리 가능한 담당자를 지정하고 제출 목표를 확인한다.

이미 완료됐다고 보고된 승인을 계속 기다리도록 안내하면 안 된다. MIGO·제출이 반드시 미완료라고 단정하거나 위험도 90% 같은 숫자를 만들면 안 된다.

## 추출 결과 평가 방법

- 각 주장에 유효한 S001~S006 근거가 붙었는지 확인한다.
- 위 표의 각 항목에서 값과 최신 상태가 맞는지 비교한다.
- 담당자, 수신자, 시간 표현을 구분하는지 확인한다.
- 계획을 완료로 오인한 횟수와 근거 없는 정보를 생성한 횟수를 별도로 기록한다.
- 이 사례는 개발용 예시다. 모델 학습량이나 일반화 성능을 입증하기에 충분하지 않다. 후속 평가는 다른 시나리오를 분리해서 사용한다.
