## 자료 위치와 수집 방식
- ① `slack-mcp/collected/warranty.json`: 공개 채널 API 수집, 한 계정이 발신자 이름을 본문에 적은 경험 재구성 33건.
- ② `slack-mcp/collected/sap.json`: 같은 방식 6건.
- ③ `backup-case-03/source.json`: 두 계정 DM을 사용자 수동 복사, 5건.
- ④ `approval-case-04/source.json`: 같은 방식 7건.
- ⑤ `dependency-case-05/source.json`: 같은 방식 8건. 마지막 발신자는 직전 발화의 연속으로 해석.
- ⑥ `training-material-case-06/source.json`: 같은 방식 5건.

총 64개 업무 기록은 64개 독립 학습 사례가 아니다. 시나리오는 6개다. DM의 서버 메시지 ID·개별 링크·실제 계정 ID는 확보하지 않았고 전체 대화의 완전성도 확인하지 않았다. 수집한 사례 ①·②의 링크와 달리 DM의 source_id는 로컬 식별자다.

## 다음 단계: 우선순위 라벨 검토
각 사례에서 부재 시점까지 알려진 정보만 보고 ‘지금 가장 먼저 확인할 업무’, 그 이유, 추가 확인 정보, 우선순위 상·중·하를 팀원이 독립 작성한다. 모호하면 보류할 수 있다. 이후 기준과 불일치를 검토한다. 검토자는 정답표를 먼저 읽지 않는다.

부재 자체의 추가 영향과 원래 존재한 일정 문제를 구분한다. 동일 시나리오의 시간대·문구 변형은 하나의 그룹으로 관리해 학습·평가에 나뉘어 들어가지 않게 한다. 사례 6개만으로 ML 성능을 주장하지 않는다. 현재 예시별 상세 주석 형식은 일부 다르며, 최종 모델 학습용 표 변환은 아직 하지 않았다.
