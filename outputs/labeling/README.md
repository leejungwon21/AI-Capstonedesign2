# 우선순위 평가 1차

## 목적
부재 직후 **개별 업무를 얼마나 먼저 확인·인계해야 하는지** 사람이 판단한다. 실제 사고 확률이나 모델 성능을 평가하는 단계가 아니다. 이번 6개는 기준을 점검하는 개발용 사례다.

## 작성 순서
1. 평가자마다 별도의 answers-template.csv 복사본을 사용한다. reviewer_id에는 A/B 같은 식별자를 적는다.
2. conversations.md에서 해당 사례의 설정과 원문만 읽는다. 기존 review.md, evaluation-only.md, case-comparison.md와 다른 사람의 답은 먼저 읽지 않는다.
3. 가장 먼저 확인할 업무 하나를 task_name에 적고, label과 이유를 작성한다. 필요하면 같은 case_id로 행을 추가해 다른 업무도 평가한다. 서로 다른 업무를 합쳐 사례 전체에 한 점수를 매기지 않는다.
4. evidence_ids에는 판단을 뒷받침하는 원문 ID를 적는다. unknowns에는 확인이 필요한 정보를 적는다.
5. 각자 작성 후 업무 범위부터 맞추고, 우선순위가 다른 이유를 논의한다. 원래 답은 보존하고 합의 결과는 별도로 기록한다. 합의하지 못한 행은 보류한다.

이미 이 대화의 해설을 읽은 평가자는 prior_exposure에 yes를 기록한다. 이 사용자의 평가는 독립적인 블라인드 평가로 간주하지 않는다. 아직 해설을 보지 않은 팀원이 원문부터 평가하면 비교에 도움이 된다.

## 공통 기준 초안
이 기준은 팀의 운영상 정의이며 검증된 산업 표준이 아니다. 마감 시간만으로 자동 판정하지 않는다.

| label | 의미 |
|---|---|
| 상 | 다음 정기 확인까지 미루기 어렵다. 당장 상태 확인·담당 배정·막힌 조건 해소에 착수할 필요가 있다. 이유를 원문으로 뒷받침한다. |
| 중 | 즉각 착수할 근거는 약하지만, 당일 중 확인·인계 계획을 정해야 한다. |
| 하 | 당일 즉시 대응의 필요성은 낮다. 다음 확인 시점과 담당을 정해 추적할 수 있다. 방치 가능을 뜻하지 않는다. |
| 보류 | 정보가 부족하거나 기준이 모호해 등급을 정할 수 없다. 필요한 정보를 적는다. |

‘보류’는 네 번째 위험 등급이 아니다. 모델 학습 라벨에서 제외하거나 재검토한다. 확인된 완료 업무를 골랐다면 남은 확인 사항이 무엇인지 명시하고, 단순히 완료라는 이유로 하 등급 학습 행을 만들지 않는다.

## 구분할 내용
- planned ≠ completed: 하겠다는 말은 완료 기록이 아니다.
- unknown ≠ absent: 대체 담당자·문서가 언급되지 않았다고 없다고 단정하지 않는다.
- 과거 수행 경험 ≠ 현재 인계 수락·권한·가용 시간.
- 원래 일정 문제와 부재로 추가되는 영향을 각각 baseline_issue, absence_impact에 쓴다.
- 최종 데이터는 업무별 행이다. 같은 시나리오의 모든 행·변형은 같은 학습/평가 그룹으로 둔다.
- 1차 평가는 ‘가장 먼저 확인할 업무’ 중심이어서 선택 편향이 있다. 모든 업무를 평가한 본 학습 데이터로 간주하지 않는다.

## 이후
6개를 평가해 모호한 기준을 수정한 뒤, 다른 구조의 사례를 늘리고 모든 대상 업무에 라벨을 작성한다. 아직 모델을 학습하거나 위험 백분율을 출력하지 않는다.
